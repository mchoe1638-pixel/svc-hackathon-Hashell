## 1. 무엇을 만드는가

영수증 사진 한 장으로 "먹은 만큼, 실제로 낸 만큼" 정산을 끝내는 해외여행 공동 가계부다. **총무는 Android 앱**으로 방을 만들고 관리하며, **동행자는 앱 설치 없이 링크 하나로 모바일 웹**에 참여한다.

| # | 핵심 기능 | 3일 내 목표 |
| --- | --- | --- |
| ① | 영수증 촬영 → 품목 단위 체크 정산 | 완성 |
| ② | 결제 수단별 실제 원화 비용 계산 | 축소 구현 (현금·카드) |
| ③ | 설치 없는 실시간 공동 가계부 + 송금 최소화 | 완성 |

주요 고객: 3~6명이 일본·동남아로 자유여행을 가는 20~30대 친구 그룹. 도입 주체는 정산을 떠안는 **총무**다. 총무 한 명만 앱을 설치하면 그룹 전체가 쓴다.

## 2. 핵심 결정 사항 (3일 동안 되돌리지 않음)

| 결정 | 근거 |
| --- | --- |
| **총무 = Android 앱(Capacitor 셸), 동행 = 모바일 웹**, 화면 코드는 하나 | 총무는 여행 내내 쓰는 사람이라 앱이 맞고, 동행은 설치 없이 참여해야 함. 화면을 한 벌로 유지해야 2인 3일 안에 끝남 |
| **Claude API (유료)** | 영수증에 개인정보 포함. 유료 API는 학습 미사용, 무료 티어는 일일 한도로 데모 날 429 위험 |
| **Spring Boot 미사용** | 3일 안에 Spring + 배포 + 실시간은 무리. Next.js Route Handler가 서버 역할. Spring 확장은 발표 슬라이드로 |
| **OCR 공급자는 교체 가능한 어댑터 뒤로** | 모델 비교(Day 2)에 어차피 필요. "고객사 계정으로 돌릴 수 있다"는 답이 됨 |
| **계산 로직은 `src/core/`에만** | 순수 함수라 테스트가 빠르고, 나중에 Spring으로 그대로 옮길 수 있음 |

### 기술 스택

- Next.js (App Router) + TypeScript
- Tailwind + shadcn/ui
- Supabase: Postgres, Realtime, 익명 로그인(Anonymous Sign-in)
- Claude API: 영수증 파싱
- Vercel: 배포 (PR마다 미리보기 주소, `main`은 운영 주소)
- Capacitor (Android): 총무 앱 셸. 운영 주소를 열고, 기본 공유창(Share) 사용
- zod (AI 응답 검증), @tanstack/react-query (데이터 캐시·낙관적 업데이트), vitest (테스트)

## 3. 사용자 플로우

**총무 (앱)**
1. hashell 앱 실행 → 방 만들기 (여행명, 현지통화, 현금 환율, 카드 수수료율, 멤버 이름)
2. 초대 링크 공유 화면 (`/trip/[id]/invite`): 공유 버튼 → 폰 기본 공유창으로 단톡방 전송, QR도 표시
3. 전원 참여 확인 → 링크 잠금 (`LOCKED`, 새 기기 참여 차단. 기존 멤버는 계속 사용)

**동행 (웹)**
4. 링크 진입 → 멤버 목록에서 자기 이름 선택 (이미 다른 기기와 묶인 이름은 선택 불가) 또는 새 이름 추가 → 홈

**함께 (앱·웹 동일 화면)**
5. 누구나 지출 추가: 영수증 촬영 또는 수기, 결제수단(현금·카드), 낸 사람
6. 영수증이면 AI 파싱 → 초안 확인·수정 → 저장 (확인 전에는 저장되지 않음)
7. 품목은 기본 전원 체크. 안 먹은 사람이 자기 체크만 해제 (총무는 대신 가능). 전원 화면에 즉시 반영
8. 지출 수정·삭제는 올린 사람·총무만. 그 사이 누가 먼저 고쳤으면 409 → 최신 내용 다시 보여주기
9. 홈: 받을 돈 / 보낼 돈 카드가 실시간 갱신

**정산 (총무가 확정)**
10. 총무: 정산 확정 (`SETTLED`) → 송금 목록 고정 (n−1회 이하). 이후 지출·체크 쓰기는 423
11. 받는 사람이 입금 확인 후 '받았어요'. 전부 받으면 정산 끝
12. 잘못 확정했으면 총무만 확정 해제 (송금 기록 초기화 경고 후 `LOCKED`로)

- 링크 공유 화면은 모달이 아니라 **독립 화면**. 새로고침해도 유지되고, 홈 상단 "N명이 아직 안 들어왔어요" 배너에서 다시 열 수 있다.
- 첫 화면(`/`)을 웹 브라우저로 열면 방 만들기 대신 "방은 hashell 앱에서 만들 수 있어요" 안내만 보인다. 이건 화면 구분이고 서버가 앱 여부를 검증하지는 않는다.

### 링크 진입 시 서버 판정

| 조건 | 결과 |
| --- | --- |
| 이미 참여한 기기(같은 익명 계정) | 바로 홈 |
| 링크 잠김 + 미참여 기기 | 참여 마감 안내 |
| 그 외 | 이름 선택 또는 새 이름 추가 화면 |

## 4. 시스템 구조

```
[총무 폰: hashell 앱 (Capacitor WebView)] ─┐
                                          ├─ 같은 Next.js 화면 (Vercel 운영 주소)
[동행 폰: 브라우저]  ──────────────────────┘
   │ 화면은 src/hooks/ + src/lib/native.ts만 호출
   ├─ 읽기·실시간 구독 ──→ [Supabase Postgres + Realtime]  (RLS로 trip 격리)
   └─ 쓰기·AI·환율 ─────→ [Next.js Route Handler: app/api/*]
                              ├─→ Claude API (영수증 파싱)
                              ├─→ 수출입은행 / Frankfurter (환율)
                              └─→ Supabase (service role로 쓰기)
```

- **읽기**: 화면(훅)이 Supabase에 직접. RLS가 "이 여행의 멤버만" 읽게 막는다.
- **쓰기**: 전부 `app/api/*`를 거친다. 서버가 멤버 여부·권한·상태·버전·금액 검증을 한다.
- **앱**: Capacitor 셸은 Vercel **운영(main) 주소**를 연다. 그래서 화면 변경은 `main`에 병합·배포돼야 앱에 반영된다.

### 서버가 반드시 맡는 일

| 일 | 클라이언트에 두면 안 되는 이유 |
| --- | --- |
| Claude API 호출 | 키가 브라우저에 노출됨 |
| 수출입은행 환율 호출 | 키 노출 + 일 1,000회 제한 → 서버에서 하루 1회 수집해 DB 캐시 |
| 참여·권한·상태 판정 | 클라이언트 검증은 검증이 아님 |
| 지출 버전 비교 (409) | 동시 수정 덮어쓰기 방지 |
| 정산 확정 스냅샷 | 신뢰 가능한 시점 기록 |

### 신원 처리 (Supabase 익명 로그인)

1. 앱 또는 링크 진입 시 `supabase.auth.signInAnonymously()` → 기기별 익명 계정 생성 (세션은 앱 WebView 또는 브라우저에 저장)
2. 방 생성 시 서버가 만든 사람의 익명 계정을 총무 멤버로 묶음
3. 이름 선택 시 서버가 `members.auth_user_id = 현재 익명 계정`으로 묶음
4. RLS: "`auth.uid()`가 이 trip의 멤버일 때만 읽기 허용"
5. 효과: 가입·비밀번호 없음, 같은 기기는 재진입 시 바로 홈, 남이 다른 이름으로 지출을 올릴 수 없음
6. 주의: **앱 WebView와 같은 폰의 브라우저는 세션이 따로다.** 총무가 같은 폰 브라우저로 링크를 열면 다른 사람으로 인식된다. 총무는 끝까지 앱으로만 쓴다
7. 폰 분실·앱 삭제 시 복구(재연결 코드)는 범위 밖

### 환경변수

`NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저 코드에 그대로 박힌다.

- 서버 전용: `ANTHROPIC_API_KEY`, `KOREAEXIM_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`
- 공개 가능: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- 개발용: `NEXT_PUBLIC_USE_MOCK` (true면 훅이 가짜 데이터를 반환)
- 앱 셸 주소는 `capacitor.config.ts`의 `server.url`에 운영 주소로 둔다 (비밀 아님)

### 정산 계산 위치

`src/core/`의 같은 함수를 두 곳에서 쓴다. 함수가 하나라 결과가 어긋나지 않는다.
- 화면: 실시간 데이터로 즉시 계산해 표시 (`useSettlement`)
- 서버: 정산 확정 시 같은 함수로 계산해 `transfers`에 스냅샷 저장

## 5. 화면 ↔ 데이터 계약 (병렬 개발의 핵심)

화면 코드는 `fetch`나 Supabase를 직접 부르지 않는다. **`src/hooks/`의 훅과 `src/lib/native.ts`만 부른다.** 데이터 모양은 `src/types/api.ts`가 정한다.

- Day 0(늦어도 D1 오전)에 둘이 같이 훅 이름·입출력 타입을 확정한다.
- 백엔드가 훅을 먼저 "가짜 데이터 반환" 버전으로 만든다 (`src/mocks/` 사용).
- 디자이너는 그 훅으로 화면을 완성한다.
- 백엔드가 훅 안쪽만 진짜 API로 바꾼다. **화면 코드는 한 줄도 안 바뀐다.**

### 훅 목록 (초안, 합의 후 확정)

| 훅 | 반환 / 하는 일 | 쓰는 화면 |
| --- | --- | --- |
| `useCreateTrip()` | 방 생성(여행명, 통화, 현금 환율, 카드 수수료율, 멤버 이름) → tripId, inviteCode | 방 만들기 (앱) |
| `useJoinInfo(inviteCode)` | 여행명, 멤버 목록(묶임 여부), 잠김 여부 | 참여 |
| `useJoinTrip()` | 이름 선택 또는 새 이름 추가 → 참여 (묶인 이름이면 409) | 참여 |
| `useTrip(tripId)` | 여행 정보, 멤버, 나(`isOrganizer`), 상태 | 전체 |
| `useExpenses(tripId)` | 지출 목록 (실시간) | 홈 |
| `useExpense(expenseId)` | 품목, 체크, 세금·봉사료, `canEdit`, `version` | 품목 체크 |
| `useSettlement(tripId)` | 사람별 잔액, 송금 목록 (확정 후엔 고정 목록 + 받음 여부) | 홈, 정산 |
| `useCreateExpense()` | 지출 추가 (수기 또는 파싱 초안 확인 후), 결제수단 포함 | 지출 추가 |
| `useUpdateExpense()` / `useDeleteExpense()` | 지출 수정·삭제 (`version` 포함, 409 처리) | 품목 체크 |
| `useParseReceipt()` | 이미지 → 파싱 초안 (confidence, needsReview 포함, 저장 안 함) | 지출 추가 |
| `useToggleShare()` | 품목 체크/해제 (낙관적 업데이트) | 품목 체크 |
| `useLockTrip()` | 링크 잠금 | 공유 |
| `useSettleTrip()` / `useUnsettleTrip()` | 정산 확정 / 확정 해제 (총무) | 정산 |
| `useMarkReceived()` | 받았어요 (받는 사람) | 정산 |

## 6. 기능 ① 영수증 → 품목 단위 체크 정산

전통 OCR 엔진은 쓰지 않는다. Claude Vision에 이미지를 바로 보내 구조화된 JSON으로 받는다 (1회 호출). 결과는 **초안으로 응답만** 하고, 사용자가 확인·수정해 저장할 때 지출이 된다. 이미지는 저장하지 않는다.

### AI가 돌려줘야 하는 것 (`ParsedReceipt`)

| 필드 | 설명 |
| --- | --- |
| 품목명 (원문 / 한국어) | 외국어 품목명과 번역 |
| 단가, 수량 | 통화 최소 단위 정수 |
| `split_type` | EACH(1인 1개) / SHARED(나눠 먹음) |
| `suggested_eaters` | 몇 명이 먹었을지 추정 (참고 표시용. 체크 기본값은 전원) |
| 소계, 세금, 봉사료, 할인, 합계 | 검증용 |
| `confidence` | high / medium / low |

### 체크 규칙

- 저장된 품목은 **방의 모든 멤버가 체크된 상태**로 시작한다.
- 각자 안 먹은 품목에서 **자기 체크만** 해제한다. 총무는 다른 사람 것도 대신 바꿀 수 있다.
- 체크가 0명이 되는 해제는 막는다 (누군가는 먹었어야 함).

### 품목 없는 영수증·카드 전표

예외 항목만 입력하고 나머지는 자동 분배한다. 총액 ¥12,000 중 "수빈 혼자 산 기념품 ¥3,000"만 입력하면 남은 ¥9,000을 체크된 인원끼리 나눈다.

### 세금·봉사료·할인 배분

각자 먹은 금액 비율대로 배분하고 **최대 잔여법**으로 1원까지 맞춘다. 동점이면 멤버 참여 순서로 정한다.

### 안전장치 (필수)

서버에서 `품목 합계 + 세금 + 봉사료 − 할인 == 총액`을 검증한다. 어긋나거나 `confidence: low`면 자동 확정하지 않고 **수동 확인 화면**으로 보낸다. 틀린 금액을 자신 있게 보여주는 것이 가장 치명적이다. 판독 자체가 실패하면 수기 입력으로 넘어간다.

## 7. 기능 ② 결제 수단별 실제 원화 비용 (축소)

**이 서비스에 실시간 환율은 거의 필요 없다.** 3일 범위에서는 두 가지 결제수단만 다룬다.

| 결제 수단 | 적용 환율 | 확정 여부 |
| --- | --- | --- |
| 현금 | 총무가 방 만들 때 입력한 환전 환율 (환전 영수증 기준) | 확정 |
| 해외 카드 | 결제일 전신환매도율(TTS) × (1 + 수수료율) | 추정 ("추정" 배지) |

- 지출 저장 시 그 시점의 환율·수수료율을 `expenses`에 **스냅샷**으로 복사한다. 이후 방 설정이나 고시 환율이 바뀌어도 과거 지출은 그대로다.
- 발표 문구: "기존 앱은 실시간 환율 하나로 전부 환산합니다. 저희는 실제로 적용된 환율을 지출마다 따로 기록합니다."

### 환율 데이터 소스

- 주력: **한국수출입은행 Open API**. `tts` = 전신환매도율, `deal_bas_r` = 매매기준율. 무료, 일 1,000회, 영업일 11시 전후 갱신.
- 보조: **Frankfurter**. 키 없음. 수출입은행에 없는 통화와 장애 시 폴백.

### 함정 두 개

1. **엔화는 100엔 단위로 온다** (`cur_unit: "JPY(100)"`). 그대로 쓰면 100배 틀린다.
2. **주말·공휴일엔 빈 배열**. 최근 영업일로 거슬러 올라가는 폴백 필수.

### 카드 청구액 공식

```latex
\text{청구원화} = \text{현지통화 금액} \times \text{TTS} \times (1 + r_{\text{수수료}})
```

| 항목 | 요율 (발표 전 카드사 공지로 재확인) |
| --- | --- |
| 국제브랜드 | Visa 약 1.1% · Mastercard 약 1% · AMEX 약 1.4% |
| 해외서비스 | 카드사별 약 0.18~0.3% |
| 합계 체감 | 약 2~2.5% (방 생성 시 기본값으로 제시, 총무가 수정 가능) |

비자·마스터의 실제 환율은 비공개라 근사치를 쓴다 (±0.5% 오차). 숨기지 않고 "추정" 배지로 표시한다. 청구 확정 금액으로 보정하는 기능은 범위 밖이다 (발표 슬라이드에서 확장 계획으로 설명).

## 8. 기능 ③ 실시간 공동 가계부 + 송금 최소화

### 실시간 동기화

Supabase Realtime으로 `expenses`, `items`, `item_shares`, `trips`, `transfers` 변경을 구독한다 (`useTripRealtime`). 체크박스는 **낙관적 업데이트**: 서버 응답을 기다리지 않고 화면에 먼저 반영하고, 실패하면 되돌린다. 총무 앱과 동행 브라우저가 같은 방식으로 받는다.

### 동시 수정 처리

| 대상 | 방식 |
| --- | --- |
| 품목 체크 | `item_shares`가 (품목, 멤버) 한 행씩이라 서로 덮어쓰지 않음. 잠금 불필요 |
| 지출 수정·삭제 | 요청에 `version`을 실어 보냄. DB 값과 다르면 409 → 화면은 최신 내용을 다시 보여줌. 성공하면 `version + 1` |

### 여행 상태 기계

| 상태 | 조건 | 신규 기기 | 기존 참여자 |
| --- | --- | --- | --- |
| OPEN | 생성 직후 | 이름 선택·새 이름 추가 가능 | 정상 |
| LOCKED | 총무가 링크 잠금 | 차단 | 정상 (지출·체크 가능) |
| SETTLED | 총무가 정산 확정 | 차단 | 읽기만 (쓰기 423), 받는 사람은 '받았어요'만 가능 |

- 확정 해제(총무만): SETTLED → LOCKED, `transfers` 삭제. 화면은 "송금 기록이 초기화돼요" 경고 후 실행.

### 송금 최소화

각자 순잔액 계산 → 최대 채권자와 최대 채무자를 매칭해 작은 쪽 금액만큼 상계 → 반복. **(인원−1)회 이하** 보장. 최적해는 NP-hard지만 6명 규모에서 그리디와 차이가 없다. 각 송금 줄에 송금 앱 딥링크 또는 계좌 복사 버튼을 붙인다. 확정 후에는 받는 사람이 '받았어요'로 완료 처리한다.

## 9. 데이터 모델과 계산 원칙

### 테이블

| 테이블 | 담는 것 |
| --- | --- |
| `trips` | 여행명, 기준통화, 현지통화, 현금 환율, 카드 수수료율, 초대코드(16자 이상), 상태 |

| `expenses` | 결제자, 올린 사람(`created_by`), 금액, 통화, 결제수단(CASH/CARD), 적용환율·수수료 스냅샷, 원화 금액, 추정 여부, `version` |
| `items` | 품목 원문·한국어명, 단가, 수량, split_type |

| `adjustments` | 세금 / 봉사료 / 할인 |
| `transfers` | 정산 확정 시 고정한 송금 (보내는 사람, 받는 사람, 원화 금액, `received_at`) |
| `exchange_rates` | 통화, 고시일, 매매기준율, 전신환매도율 |
| `ai_usage` | 여행별 일일 AI 호출 수 (남용 방지) |

### 깨뜨리면 안 되는 원칙

1. 금액은 **통화 최소 단위 정수**. float 금지.
2. 환산은 **지출 단위**. 환율은 지출 생성 시점에 `expenses`에 **스냅샷으로 복사**한다. 조인해서 그때그때 계산하면 고시 수정 시 과거 정산이 바뀐다.
3. 계산 로직은 `src/core/`에만. 화면은 표시만.

### 테스트로 고정할 케이스

- 세금·봉사료 배분 후 합계가 원래 금액과 정확히 일치
- 동점 잔여 배분이 참여 순서로 결정됨
- 엔화 100단위 환산
- EACH / SHARED 혼재 영수증
- 체크 해제한 사람의 몫은 0
- 품목 없는 전표의 예외 항목 + 나머지 균등 분할
- 같은 외화 금액을 현금·카드로 냈을 때 원화가 다름
- 송금 횟수 ≤ 인원−1, 전원 잔액 합계 0
- 환율이 다른 지출 2개를 같은 사람이 나눠 먹는 경우

### 업로드 전 이미지 리사이즈

폰 사진(약 5MB)을 브라우저에서 긴 변 1500px, JPEG 0.8로 줄이면 약 200KB. 업로드가 5초 → 0.5초로 줄어 데모 체감이 가장 크게 좋아진다. (`src/lib/image/resize.ts`, 백엔드 작성 → 촬영 화면에서 훅을 통해 사용)

## 13. 발표 구성과 질문 대비

### 5분 발표

| 시간 | 내용 |
| --- | --- |
| 30초 | 일본 여행 3일 정산 실패 실화 |
| 30초 | 기존 방식이 안 되는 이유: 기록 분산, 총액 분할, 환율 불명확 |
| 2분 30초 | **라이브 데모**: 총무가 앱으로 방 생성 → 공유창·QR로 심사위원이 웹으로 참여 → 영수증 촬영 → 심사위원이 체크 해제 → 총무 앱 금액 즉시 변경 → 정산 확정 |
| 1분 | AI 파싱 · 환율 · 동기화 구조, 모델 비교 표 |
| 30초 | Spring 기반 확장 설계 + 출시 계획 |

### 예상 질문

- 링크만 있으면 아무나 보나요? → 16자 이상 초대코드 + 전원 참여 후 잠금 + 기기별 익명 계정 묶기
- 왜 총무만 앱이에요? → 여행 내내 쓰는 사람은 한 명. 나머지는 설치 장벽 없이 참여해야 그룹 전체가 씀
- AI가 틀리면요? → 합계 검증 실패나 low면 수동 확인. 판독 결과는 확인 전까지 저장되지 않음
- 두 사람이 동시에 고치면요? → 체크는 사람별 행이라 충돌 없음, 지출 수정은 버전 비교로 늦은 쪽을 막고 최신 내용을 보여줌
- 실시간 환율은? → 정산에 쓰지 않는다. 실제 적용 환율을 지출마다 기록
- 송금 최소화는 최적해인가요? → n−1 상한 보장, 6명 규모에서 최적해와 일치
- 비용은? → 영수증 1장 약 10~30원 (모델별 표 준비), 여행당 일일 쿼터

### 파는 것은 OCR이 아니다

OCR은 누구나 한다. 자산은 품목 단위 분할 엔진, 결제수단별 실환율 계산, 송금 최소화 + 1원 정합성, 총무 한 명만 설치하면 되는 참여 구조다. 확장성(BYOK, 국내 리전 전환, 평가셋)은 슬라이드로만 말하고, 실제 구현은 **공급자 어댑터**와 **합계 검증 + confidence 폴백** 두 개만 한다.
