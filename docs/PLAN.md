## 1. 무엇을 만드는가

영수증 사진 한 장으로 "먹은 만큼, 실제로 낸 만큼" 정산을 끝내는 해외여행 공동 가계부 **모바일 웹**이다. 동행자는 앱 설치 없이 링크 하나로 참여한다.

| # | 핵심 기능 | 3일 내 목표 |
| --- | --- | --- |
| ① | 영수증 촬영 → 품목 단위 체크 정산 | 완성 |
| ② | 결제 수단별 실제 원화 비용 계산 | 축소 구현 |
| ③ | 설치 없는 실시간 공동 가계부 + 송금 최소화 | 완성 |

주요 고객: 3~6명이 일본·동남아로 자유여행을 가는 20~30대 친구 그룹. 도입 주체는 정산을 떠안는 **총무**다.

## 2. 핵심 결정 사항 (3일 동안 되돌리지 않음)

| 결정 | 근거 |
| --- | --- |
| 네이티브 앱이 아닌 **모바일 웹** | 차별점이 "설치 없이 링크 참여". 데모에서 심사위원 폰에 QR로 바로 참여시킬 수 있는 것도 웹뿐 |
| **Claude API (유료)** | 영수증에 개인정보 포함. 유료 API는 학습 미사용, 무료 티어는 일일 한도로 데모 날 429 위험 |
| **Spring Boot 미사용** | 3일 안에 Spring + 배포 + 실시간은 무리. Next.js Route Handler가 서버 역할. Spring 확장은 발표 슬라이드로 |
| **OCR 공급자는 교체 가능한 어댑터 뒤로** | 모델 비교(Day 2)에 어차피 필요. "고객사 계정으로 돌릴 수 있다"는 답이 됨 |
| **계산 로직은 `src/core/`에만** | 순수 함수라 테스트가 빠르고, 나중에 Spring으로 그대로 옮길 수 있음 |

- Next.js (App Router) + TypeScript

- Supabase: Postgres, Realtime, Storage, 익명 로그인(Anonymous Sign-in)

## 3. 사용자 플로우

1. 총무: 방 만들기 (여행명, 현지통화, 멤버 이름 입력)
2. 총무: 초대 링크·QR 공유 화면 (`/trip/[id]/invite`)
3. 동행자: 링크 진입 → 멤버 목록에서 자기 이름 선택 → 홈
4. 총무: 전원 참여 확인 → 링크 잠금
5. 누구나: 지출 추가 (영수증 촬영 / 카드 문자 붙여넣기 / 수기)
6. AI 파싱 → 품목 목록 + 체크 제안
7. 각자: 자기가 먹은 품목 체크 (전원 화면에 즉시 반영)
8. 홈: 받을 돈 / 보낼 돈 카드가 실시간 갱신
9. 총무: 정산 확정 → 송금 목록 (n−1회 이하)

- 링크 공유 화면은 모달이 아니라 **독립 화면**. 새로고침해도 유지되고, 홈 상단 "N명이 아직 안 들어왔어요" 배너에서 다시 열 수 있다.

### 링크 진입 시 서버 판정

| 조건 | 결과 |
| --- | --- |
| 이미 참여한 기기(같은 익명 계정) | 바로 홈 |
| 링크 잠김 + 미참여 기기 | 참여 마감 안내 |
| 그 외 | 이름 선택 화면 |

## 4. 시스템 구조

```
[브라우저: Next.js 화면]
   │ 화면은 src/hooks/만 호출
   ├─ 읽기·실시간 구독 ──→ [Supabase Postgres + Realtime]  (RLS로 trip 격리)
   └─ 쓰기·AI·환율 ─────→ [Next.js Route Handler: app/api/*]
                              ├─→ Claude API (영수증·문자 파싱)
                              ├─→ 수출입은행 / Frankfurter (환율)
                              └─→ Supabase (service role로 쓰기)
```

- **읽기**: 화면(훅)이 Supabase에 직접. RLS가 "이 여행의 멤버만" 읽게 막는다.
- **쓰기**: 전부 `app/api/*`를 거친다. 서버가 멤버 여부·상태(잠금/확정)·금액 검증을 한다.

### 서버가 반드시 맡는 일

| 일 | 클라이언트에 두면 안 되는 이유 |
| --- | --- |
| Claude API 호출 | 키가 브라우저에 노출됨 |
| 수출입은행 환율 호출 | 키 노출 + 일 1,000회 제한 → 서버에서 하루 1회 수집해 DB 캐시 |
| 참여·잠금 판정 | 클라이언트 검증은 검증이 아님 |
| 영수증 이미지 저장 | 용량·권한 |
| 정산 확정 스냅샷 | 신뢰 가능한 시점 기록 |

### 신원 처리 (Supabase 익명 로그인)

1. 링크 진입 시 `supabase.auth.signInAnonymously()` → 기기별 익명 계정 생성 (세션은 브라우저에 저장)
2. 이름 선택 시 서버가 `members.auth_user_id = 현재 익명 계정`으로 묶음
3. RLS: "`auth.uid()`가 이 trip의 멤버일 때만 읽기 허용"
4. 효과: 가입·비밀번호 없음, 같은 기기는 재진입 시 바로 홈, 남이 다른 이름으로 지출을 올릴 수 없음
5. 폰 분실: 총무 화면에서 해당 멤버에 **1회용 재연결 코드** 발급 → 새 기기의 익명 계정으로 다시 묶음

### 환경변수

`NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저 코드에 그대로 박힌다.

- 서버 전용: `ANTHROPIC_API_KEY`, `KOREAEXIM_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`
- 공개 가능: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- 개발용: `NEXT_PUBLIC_USE_MOCK` (true면 훅이 가짜 데이터를 반환)

### 정산 계산 위치

`src/core/`의 같은 함수를 두 곳에서 쓴다. 함수가 하나라 결과가 어긋나지 않는다.
- 화면: 실시간 데이터로 즉시 계산해 표시 (`useSettlement`)
- 서버: 정산 확정 시 같은 함수로 계산해 스냅샷 저장

## 5. 화면 ↔ 데이터 계약 (병렬 개발의 핵심)

화면 코드는 `fetch`나 Supabase를 직접 부르지 않는다. **`src/hooks/`의 훅만 부른다.** 데이터 모양은 `src/types/api.ts`가 정한다.

- Day 1 오전에 둘이 같이 훅 이름·입출력 타입을 확정한다.
- 백엔드가 훅을 먼저 "가짜 데이터 반환" 버전으로 만든다 (`src/mocks/` 사용).
- 디자이너는 그 훅으로 화면을 완성한다.
- 백엔드가 훅 안쪽만 진짜 API로 바꾼다. **화면 코드는 한 줄도 안 바뀐다.**

### 훅 목록 (초안, Day 1 오전 확정)

| 훅 | 반환 / 하는 일 | 쓰는 화면 |
| --- | --- | --- |
| `useCreateTrip()` | 방 생성 → tripId, inviteCode | 방 만들기 |
| `useJoinInfo(inviteCode)` | 여행명, 멤버 목록, 잠김 여부 | 참여 |
| `useJoinTrip()` | 이름 선택 → 참여 | 참여 |
| `useTrip(tripId)` | 여행 정보, 멤버, 나, 상태 | 전체 |
| `useExpenses(tripId)` | 지출 목록 (실시간) | 홈 |
| `useExpense(expenseId)` | 품목, 체크, 세금·봉사료 | 품목 체크 |
| `useSettlement(tripId)` | 사람별 잔액, 송금 목록 | 홈, 정산 |
| `useCreateExpense()` | 수기 지출 추가 | 지출 추가 |
| `useParseReceipt()` | 이미지 → 파싱 결과 (confidence 포함) | 지출 추가 |
| `useParseSms()` | 문자 → 지출 후보 | 지출 추가 |
| `useToggleShare()` | 품목 체크/해제 (낙관적 업데이트) | 품목 체크 |
| `useAddFxPurchase()` | 환전 등록 | 환전 |
| `useLockTrip()` / `useSettleTrip()` | 링크 잠금 / 정산 확정 | 공유, 정산 |

모든 훅은 `{ data, isLoading, error }` 형태를 따른다 (react-query 기본 형태).

### 화면이 알아야 하는 상태 필드 (`api.ts`에 포함)

| 필드 | 붙는 곳 | 화면 처리 |
| --- | --- | --- |
| `needsReview: boolean` | 영수증 파싱 결과 | true면 수동 확인 화면 |
| `isEstimated: boolean` | 지출의 원화 금액 | true면 "추정" 배지 |
| `status: 'OPEN' \| 'LOCKED' \| 'SETTLED'` | 여행 | 잠금 버튼, 읽기 전용 처리 |
| `isOrganizer: boolean` | 멤버(나) | 총무 전용 버튼 표시 |

### 화면에 제공하는 공통 도구 (백엔드 작성)

- `src/core/money.ts`의 `formatMoney(amount, currency)`: 정수 금액 → `¥3,960`, `₩93,400`
- `src/lib/providers.tsx`: react-query·Supabase Provider. 디자이너는 `app/layout.tsx`에서 감싸기만
- `useTripRealtime(tripId)`: `useExpenses`·`useExpense` 안에서 자동 구독. 화면이 따로 부를 필요 없음

## 6. 기능 ① 영수증 → 품목 단위 체크 정산

전통 OCR 엔진은 쓰지 않는다. Claude Vision에 이미지를 바로 보내 구조화된 JSON으로 받는다 (1회 호출).

### AI가 돌려줘야 하는 것 (`ParsedReceipt`)

| 필드 | 설명 |
| --- | --- |
| 품목명 (원문 / 한국어) | 외국어 품목명과 번역 |
| 단가, 수량 | 통화 최소 단위 정수 |
| `split_type` | EACH(1인 1개) / SHARED(나눠 먹음) |
| `suggested_eaters` | 몇 명이 먹었을지 추정 |
| 소계, 세금, 봉사료, 할인, 합계 | 검증용 |
| `confidence` | high / medium / low |


### 품목 없는 영수증·카드 전표

예외 항목만 입력하고 나머지는 자동 분배한다. 총액 ¥12,000 중 "수빈 혼자 산 기념품 ¥3,000"만 입력하면 남은 ¥9,000을 체크된 인원끼리 나눈다.

### 세금·봉사료·할인 배분

각자 먹은 금액 비율대로 배분하고 **최대 잔여법**으로 1원까지 맞춘다. 동점이면 멤버 참여 순서로 정한다.

### 안전장치 (필수)

서버에서 `품목 합계 + 세금 + 봉사료 − 할인 == 총액`을 검증한다. 어긋나거나 `confidence: low`면 자동 확정하지 않고 **수동 확인 화면**으로 보낸다. 틀린 금액을 자신 있게 보여주는 것이 가장 치명적이다.

## 7. 기능 ② 결제 수단별 실제 원화 비용

**이 서비스에 실시간 환율은 거의 필요 없다.** 필요한 환율은 세 종류인데 실시간인 것이 없다.

| 결제 수단 | 적용 환율 | 확정 여부 |
| --- | --- | --- |
| 환전한 현금 | 환전 시 실효환율 (낸 원화 ÷ 받은 외화) | 확정 |
| 해외 카드 | 결제일 전신환매도율 × (1 + 수수료) | 추정 → 청구 문자로 확정 |
| 트래블카드 | 충전 시 환율 | 확정 |

발표 문구: "기존 앱은 실시간 환율 하나로 전부 환산합니다. 저희는 실제로 적용된 환율을 지출마다 따로 기록합니다."

### 환율 데이터 소스

- 주력: **한국수출입은행 Open API**. `tts` = 전신환매도율, `deal_bas_r` = 매매기준율. 무료, 일 1,000회, 영업일 11시 전후 갱신.
- 보조: **Frankfurter**. 키 없음. 수출입은행에 없는 통화와 장애 시 폴백.

### 함정 두 개

1. **엔화는 100엔 단위로 온다** (`cur_unit: "JPY(100)"`). 그대로 쓰면 100배 틀린다.
2. **주말·공휴일엔 빈 배열**. 최근 영업일로 거슬러 올라가는 폴백 필수.

### 카드 청구액 공식

```latex
\text{청구원화} = \text{USD금액} \times \text{TTS} \times (1 + r_{\text{브랜드}} + r_{\text{해외서비스}})
```

| 항목 | 요율 (발표 전 카드사 공지로 재확인) |
| --- | --- |
| 국제브랜드 | Visa 약 1.1% · Mastercard 약 1% · AMEX 약 1.4% |
| 해외서비스 | 카드사별 약 0.18~0.3% |
| 합계 체감 | 약 2~2.5% |

비자·마스터의 현지통화→달러 환율은 비공개라 근사치를 쓴다 (±0.5% 오차). 숨기지 않고 UI에 "추정" 배지로 표시하고, 청구 문자를 붙여넣으면 배지가 사라진다.

### 현금과 남은 외화

- 환전 등록: 낸 원화와 받은 외화 → 실효환율 역산. 누가 얼마씩 냈는지 기록 (공금)
- 여러 번 환전: 평균 실효환율 (FIFO는 범위 밖)
- 남은 현금: 여행 종료 시 가져간 사람에게 그만큼 채무 추가

### 카드 문자 파싱

승인 문자 붙여넣기 → 금액·통화·가맹점·시각 → 지출 등록. 청구 문자는 (금액, 통화, 날짜 ±3일)로 기존 지출 후보를 찾고 **사용자가 확인**한다.

## 8. 기능 ③ 실시간 공동 가계부 + 송금 최소화

### 실시간 동기화

Supabase Realtime으로 `expenses`, `item_shares` 변경을 구독한다 (`useTripRealtime`). 체크박스는 **낙관적 업데이트**: 서버 응답을 기다리지 않고 화면에 먼저 반영하고, 실패하면 되돌린다.

### 링크 상태 기계

| 상태 | 조건 | 신규 기기 | 기존 참여자 |
| --- | --- | --- | --- |
| OPEN | 생성 직후 | 이름 선택 가능 | 정상 |
| LOCKED | 총무가 잠금 | 차단 (재연결 코드만 허용) | 정상 |
| SETTLED | 총무가 정산 확정 | 차단 | 읽기만 |

### 송금 최소화

각자 순잔액 계산 → 최대 채권자와 최대 채무자를 매칭해 작은 쪽 금액만큼 상계 → 반복. **(인원−1)회 이하** 보장. 최적해는 NP-hard지만 6명 규모에서 그리디와 차이가 없다. 각 송금 줄에 송금 앱 딥링크 또는 계좌 복사 버튼을 붙인다.

## 9. 데이터 모델과 계산 원칙

### 테이블

| 테이블 | 담는 것 |
| --- | --- |
| `trips` | 여행명, 기준통화, 현지통화, 초대코드(16자 이상), 상태 |
| `members` | 이름, `auth_user_id`, 참여 순서, 참여 시각, 총무 여부 |
| `fx_purchases` | 환전 기록: 낸 원화, 받은 외화, 실효환율 |
| `fx_contributions` | 환전 공금의 1인별 지분 |
| `expenses` | 결제자, 금액, 통화, 결제수단, 적용환율 스냅샷, 추정/확정 원화 |
| `items` | 품목 원문·한국어명, 단가, 수량, split_type |
| `item_shares` | 체크한 사람만 행으로 존재 |
| `adjustments` | 세금 / 봉사료 / 할인 |
| `leftover_fx` | 남은 외화와 가져간 사람 |
| `exchange_rates` | 통화, 고시일, 매매기준율, 전신환매도율 |
| `ai_usage` | 여행별 일일 AI 호출 수 (남용 방지) |

### 깨뜨리면 안 되는 원칙

1. 금액은 **통화 최소 단위 정수**. float 금지.
2. 환산은 **지출 단위**. 환율은 지출 생성 시점에 `expenses`에 **스냅샷으로 복사**한다. 조인해서 그때그때 계산하면 고시 수정 시 과거 정산이 바뀐다.
3. 계산 로직은 `src/core/`에만. 화면은 표시만.

### 테스트로 고정할 케이스

- 세금·봉사료 배분 후 합계가 원래 금액과 정확히 일치
- 동점 잔여 배분이 참여 순서로 결정됨
- 엔화 100단위 환산
- EACH / SHARED 혼재 영수증
- 품목 없는 전표의 예외 항목 + 나머지 균등 분할
- 송금 횟수 ≤ 인원−1
- 환율이 다른 지출 2개를 같은 사람이 나눠 먹는 경우

### 5분 발표

| 시간 | 내용 |
| --- | --- |
| 30초 | 일본 여행 3일 정산 실패 실화 |
| 30초 | 기존 방식이 안 되는 이유: 기록 분산, 총액 분할, 환율 불명확 |

| 1분 | AI 파싱 · 환율 · 동기화 구조, 모델 비교 표 |
| 30초 | Spring 기반 확장 설계 + 출시 계획 |

### 예상 질문

- 링크만 있으면 아무나 보나요? → 16자 이상 초대코드 + 전원 참여 후 잠금 + 기기별 익명 계정 묶기
- AI가 틀리면요? → 합계 검증 실패나 low면 수동 확인. AI를 맹신하지 않는 설계
- 실시간 환율은? → 정산에 쓰지 않는다. 실제 적용 환율을 지출마다 기록
- 송금 최소화는 최적해인가요? → n−1 상한 보장, 6명 규모에서 최적해와 일치
- 비용은? → 영수증 1장 약 10~30원 (모델별 표 준비), 여행당 일일 쿼터

### 파는 것은 OCR이 아니다

OCR은 누구나 한다. 자산은 품목 단위 분할 엔진, 결제수단별 실환율 계산, 송금 최소화 + 1원 정합성, 설치 없는 참여 구조다. 확장성(BYOK, 국내 리전 전환, 평가셋)은 슬라이드로만 말하고, 실제 구현은 **공급자 어댑터**와 **합계 검증 + confidence 폴백** 두 개만 한다.
